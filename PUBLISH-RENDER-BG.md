# Публикуване на „Корен“ — защитена тестова версия (Render)

**Тази версия е само за проби, НЕ за реални поръчки или реални плащания.** Използвай измислени имена, телефони и адреси; не въвеждай действителни клиентски лични данни. Включена е отделна HTTP парола за целия тестов сайт, а Stripe live ключове са блокирани при включен staging режим.

## 0. Запази съществуващия си магазин

На Mac спри локалния сървър с Ctrl+C и архивирай сегашната папка `koren-grocery`, **включително скритата `.data` папка**. Тя съдържа локалните продукти, поръчки и секрет на сесиите. Не я качвай в GitHub. Публикуваната тестова версия създава **отделна** празна база с примерните продукти: не прехвърля локалните клиентски данни или направени тестови поръчки.

## 1. GitHub (проект без тайни)

1. Разархивирай този пакет в отделна папка, например `~/Projects/koren-staging`.
2. Създай ново **private** GitHub хранилище, например `koren-staging`, без автоматично генериран README.
3. Качи файловете от пакета. Ако работиш през Terminal от папката на пакета:

   ```bash
   git init
   git add .
   git status      # ПРОВЕРИ: няма .data, .env или секретни ключове
   git commit -m "Prepare protected Koren staging"
   git branch -M main
   git remote add origin URL_NA_TVOETO_NOVO_PRIVATE_REPO
   git push -u origin main
   ```

Ако GitHub поиска вход, използвай официалното му удостоверяване; не копирай Stripe ключове или администраторски пароли в GitHub.

## 2. Render Blueprint (платена услуга)

1. Отвори https://dashboard.render.com/ и избери **New → Blueprint**.
2. Свържи **private** хранилището от стъпка 1. Render ще прочете готовия `render.yaml`.
3. Преди създаването провери показаните **цени** и избрания план. Blueprint-ът изисква *платен web service* и *постоянен диск от 1 GB*; не потвърждавай, ако не желаеш месечни разходи.
4. Въведи три нови стойности, когато Render ги поиска:
   - `STAGING_HTTP_USER`: потребител за допълнителната защита на целия тестов сайт;
   - `STAGING_HTTP_PASSWORD`: нова, уникална парола с поне 12 символа;
   - `ADMIN_PASSWORD`: **друга**, уникална парола с поне 12 символа за `/admin`.
5. Render ще генерира и запази `SESSION_SECRET`. Изчакай успешно разгръщане и отвори Render URL-а. Браузърът трябва първо да поиска паролата за **тестовия сайт**, а `/admin` — отделната администраторска парола.

Default URL от Render се открива автоматично. Ако свържеш собствен домейн, задай в Render Environment `APP_BASE_URL=https://твоя-домейн` и направи нов deploy. Не записвай пароли в `.env.example`.

## 3. Stripe — тестове след публикуване

1. **Не използвай стария `whsec_` ключ от локалния Stripe CLI.** В [Stripe Dashboard](https://dashboard.stripe.com/test/workbench/webhooks) създай тестова *webhook destination* с публичен URL `https://TVOIAT-RENDER-URL/api/stripe/webhook`.
2. Абонирай destination за `checkout.session.completed`, `checkout.session.async_payment_succeeded`, `checkout.session.async_payment_failed` и `checkout.session.expired`.
3. От Stripe копирай **новия signing secret на тази destination** (`whsec_...`). В Render → Service → **Environment** добави `STRIPE_SECRET_KEY=sk_test_...` и `STRIPE_WEBHOOK_SECRET=whsec_...`. Не ги записвай във файловете на проекта или снимки.
4. Запази промените и направи redeploy. Направи тестова поръчка с измислени данни и провери в Stripe dashboard, Render logs и `/admin`, че е отчетена като **платена**.
5. Ако тестов webhook получи `400`, увери се, че ключът е на **точната** публична destination и че Stripe работи в тестова среда. Публичният Stripe endpoint е умишлено изключение от общата тестова HTTP парола: криптографският Stripe подпис продължава да се проверява.

`./stripe-listen.command` е **само за локалния Mac**. Той не е необходим на Render.

## 4. Преди истински клиенти и live плащания

- Отделен production deployment и надеждни автоматични външни backup-и с тест за възстановяване на базата.
- Ограничаване на автоматизирани поръчки и опити за вход, мониторинг и процес за сверяване на Stripe плащанията със записите в базата.
- Реална фирмена информация, доставка, наличности, политика за личните данни, условия за продажба и изискванията за търговия с храни.
- Проверка на сигурността на администрацията, API-то и зависимостите.

**Не изключвай `KOREN_STAGING_ONLY=1` просто за да приемаш истински плащания.** Това е специално защитена тестова конфигурация.
